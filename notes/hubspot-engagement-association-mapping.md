For the daily deal-review cache sync: `query_crm_data` returns deal associations inline ONLY for NOTE queries (`SELECT hs_object_id, DEAL.hs_object_id FROM NOTE WHERE DEAL.hs_object_id IN (...)` — associations appear in each result row). EMAIL and CALL queries do NOT return associations, and `FROM DEAL` with `EMAIL.x` in SELECT errors out.

Workaround used (2026-07-10): one batched NOTE query for all stale deals, then per-deal EMAIL/CALL queries filtered with `hs_createdate >= <last sync − 1 day>` so each returns only new engagements (usually 0-3 rows).

Update 2026-07-13: unfiltered batched NOTE queries now exceed the MCP response token limit (association payloads inline full contact/company property dumps) — add the same `hs_createdate >= <last sync − 1 day>` filter to the batched NOTE query too, then extract note→deal pairs. If a response is still oversized it's saved to a host-side file; extract pairs with Grep `-o` (deal id = objectId following a 46-to-3 marker).

Update 2026-07-15: account-wide delta candidate queries are UNUSABLE (`FROM EMAIL WHERE hs_createdate >= <date>` returned 19,667 org-wide emails for a 2-day window; calls 2,266). Best method: per-stale-deal filtered delta queries — `SELECT hs_object_id FROM EMAIL|CALL WHERE DEAL.hs_object_id = '<deal_id>' AND hs_createdate >= <last sync − 1 day>` works directly (the association filter is valid in WHERE even though EMAIL/CALL don't return associations in results); each returns 0-9 rows, batches 6-8 in parallel per message, 2×N queries for N stale deals (typical N≈15). May return extra deals outside review scope (e.g. duplicate company deals) — filter to the deals.json set before linking. Fetch bodies one email per get_crm_objects call. Limitation: an old email/call newly re-associated to a deal is missed — a `plan --full-refresh` catches it.

Standard scope: owners 900000113 (AE_13), 900000115 (AE_27), 900000080 (SDR_Q), 900000015 (AE_74); 19 open-stage IDs are in `scripts/build_review.py` STAGE map.

Update 2026-07-21: batched deal-filtered mapping works for NOTES — `SELECT hs_object_id, DEAL.hs_object_id FROM NOTE WHERE DEAL.hs_object_id IN (all stale) AND hs_createdate >= <cutoff>` returns note→deal TSV in one query. CALL mapping works via `SELECT hs_object_id, DEAL.hs_object_id FROM CALL WHERE hs_object_id IN (new call ids)`. EMAIL cross-object select STILL broken — `WHERE hs_object_id IN` errors ("internal error"), and `WHERE DEAL.hs_object_id IN + createdate` silently drops the DEAL column. Email→deal mapping requires reverse lookup: `search_crm_objects` objectType=deals, filterGroups=[{associatedWith:[{objectType:"emails",operator:"EQUAL",objectIdValues:[emailId]}]}], one per new email; filter to the in-scope deals.json set (some emails link to 2 deals). query_crm_data can't paginate (no offset) — to get all IDs past 25, split hs_createdate into date buckets with BETWEEN. Body fetch: get_crm_objects with 5+ emails exceeds the token limit and auto-saves the full JSON to a host tool-results file; deliberately batch big to spill bodies to disk, then parse with python json.load (strip to first '{'). Write tool overwrites on the mounted folder can leave trailing null bytes when new content is shorter — strip with `rstrip(b'\x00')` before json.load.

Update 2026-09-02 (DEAL side): batched `DEAL.hs_object_id IN (<stale ids>) AND hs_createdate >= <cutoff>` returns the DEAL column for NOTE (CALL unreliable, see 2026-09-08). EMAIL still one query per stale deal; 53 deals split across 4 subagents finished in ~40s per slice. Notes and calls are safe in main context except Proshort AI meeting-summary notes (~11k chars each) — fetch those alone; emails always go to a subagent that writes JSON to a file.

Update 2026-08-17 (COMPANY-side, no-deal segment): batched `IN` with the COMPANY column works for NOTE, CALL and MEETING_EVENT — `SELECT hs_object_id, COMPANY.hs_object_id, hs_meeting_title, hs_meeting_outcome, hs_meeting_start_time FROM MEETING_EVENT WHERE COMPANY.hs_object_id IN (...)`. EMAIL still drops the COMPANY column in the `IN` form, so emails remain one query per company with `LIMIT 100`. Do NOT select `hs_meeting_body` (Teams invite boilerplate, ~4k chars each). CLI gotcha: `engagement_cache.py` wants `--db` BEFORE the subcommand (`engagement_cache.py --db cache/x.db need-bodies --in ...`). Some companies return 0 company-associated emails even when notes/calls exist — emails are contact-associated only; expected.

Update 2026-09-08: NEVER select `hs_body_preview` on a NOTE query — Proshort notes return the full ~8-10k-char body inline. Select only `hs_object_id`, `DEAL.hs_object_id`, `hs_createdate`. When a delta query returns empty, sanity-check with a wider date window, ID columns only. The batched `CALL ... WHERE DEAL.hs_object_id IN (...)` form returned rows with NO association field — treat CALL→deal mapping as needing the `WHERE hs_object_id IN (<new call ids>)` reverse form.

Update 2026-09-09: per-deal `SELECT hs_object_id FROM CALL WHERE DEAL.hs_object_id = '<id>' AND hs_createdate >= <cutoff>` is the reliable CALL delta query. `hs_email_text` comes back blank on a minority of logged emails (HTML-only or auto-logged). Store them anyway; an empty body must NOT be treated as a fetch failure or it will be re-fetched every run.
